# 公开协作与资料边界

March 7th 的公开工程记录必须足够支撑外部贡献；内部工作记录不需要全部公开。一类可编辑事实只有一个正式维护位置，其他位置仅保存链接或注明核对时间的摘要。

## 资料与字段归属

| 内容 | 正式维护位置 | 另一侧如何使用 |
| --- | --- | --- |
| 可公开缺陷、工程任务、范围与技术验收标准 | GitHub Issue / PR | 飞书引用任务标识和工程状态，不另写一份正文 |
| 代码、测试、设计决策、贡献指南与必要验证依据 | 仓库及 PR | 飞书建立索引，不成为必要规范的唯一入口 |
| 内部负责人分工、具体排期、资源协调、试用安排 | 受限飞书项目或任务表 | 公开侧只保留参与贡献所需的约定 |
| 原始排查流水、临时提示词、Agent 接力与受限截图 | 受限飞书文档或团队批准的私有存储 | 提炼、脱敏后公开根因、结论和可复现证据 |
| 产品验收决定 | 指定验收人确认的记录 | 在公开 PR 中保留必要摘要与适用提交，不暴露私人信息 |
| 凭据与访问令牌 | 凭据管理机制 | 两端文档均不保存密钥正文 |

飞书中的内部子任务和 GitHub 的工程任务可以是一对多关系，不能因为内部子任务勾选完成就自动关闭公开工程任务。对外路线图与设计讨论仍可直接在 GitHub 维护。

## 公开任务的最低上下文

任务应包含问题或目标、复现或使用场景、范围及不做事项、设计约束、验收方法和相关基线。PR 补充实际改动、取舍、测试证据、兼容影响、未验证项目及回退方式。

公开记录不能仅引用不可访问的飞书文档。架构结论、已知缺陷、技术债和不利测试结果不因迁移内部记录而被隐藏。任务关闭、代码合并、构建生成、部署或安装验证、产品验收是不同事件。

## 平台与状态

同一共享行为仍需按 [贡献约定](../CONTRIBUTING.md) 在同一提交完成 Windows 与 macOS 验收。记录“未测”“受阻”而不是默认通过；文档变更不产生新的实机通过结论。

内部任务表分别设置开发状态、发布状态和业务验收字段。工程状态以 GitHub 可核验事实为依据，内部排期以飞书为依据；不要让双方同时写同一个状态字段。PR 未合并而关闭时标记取消或替代，不能标为已经交付。

同步只能回传经过允许的字段、来源标识和时间。先做显式链接与人工核对，再接自动化。自动同步必须处理重复事件、旧事件覆盖、失败重试和权限错误；不得把聊天机器人通知成功当作任务记录写入成功。尚未接入或未核验的自动化不能宣称已经启用。

## 旧资料的渐进整理

1. 固定来源分支、提交、路径和内容哈希；区分公开规范、历史证据、内部流水与混合文档。
2. 先提取并保留外部贡献所必需的技术约束、验证方法和已知限制。
3. 将需要受限保存的原件归档到已确认的飞书空间，核对权限、正文、附件和来源；读回成功后记录归档标识。
4. 修复公开引用，并通过独立 PR 删除或精简不再需要的过程记录。归档未成功时不删除唯一原件。

`development/app/TODO.md` 和 `development/app/WINDOWS-HANDOFF.md` 需要逐段判断，不能仅凭文件名整体删除。`development/codex-pet/` 中的行为与视觉规范仍属于公开工程资料。

仓库中的普通分支、名为 internal 的目录和 `.gitignore` 都不是保密边界。已有历史中的内容不会因文件改名、忽略或删除而消失；发现凭据泄露应单独处置，不通过普通文档整理掩盖问题。本规则不授权重写历史、改变可见性、放宽素材分发范围或发布产品。
