## 1. 产品方向与当前起点

长期计划决定方向、依赖和取舍；短期 Goal 每次只完成一个可验证结果，不把整个路线图作为一个执行目标。

## 2. 阶段依赖与验收

核心路径为：**基线与测试分发 → 桌面常驻 →〔角色体验、提醒验证并行〕→ 双角色完整试用 → 根据反馈选择后续方向。**

| 阶段 | 用户价值与范围 | 前置条件 | 完成与继续投入依据 |
|---|---|---|---|
| **M0：可信基线** | 提供同一提交的双平台测试构建、版本识别和共用清单；完成本次架构回归 | 已合并架构 | 自动检查通过；两平台实测有记录；设备缺口明确保留 |
| **M1：可靠常驻** | 托盘、退出、显示／隐藏、穿透与恢复、位置保存和越界恢复 | M0 关闭 | 不依赖终端即可控制、找回和退出桌宠；双平台行为一致 |
| **M2：角色体验** | 点击动作、情境短句、第二角色、切换及选择保存 | M1；角色候选与参考由所有者确认 | 两个真实角色使用同一套逻辑；视觉、动作、台词通过验收；切换不影响应用进度 |
| **M3：提醒价值验证** | 三类提醒、分别完成、全局稍后、合并提示、待处理入口；先用三月七原型试用 | M1；与 M2 并行 | 提醒规则、恢复场景通过测试；获得真实反馈，证明值得继续完善 |
| **M4：首个完整日用版本** | 合并双角色、提醒、必要设置、数据迁移和测试版安装体验；朋友试用两周 | M2、M3 完成 | 提醒有用且不烦，稳定底线满足；根据反馈决定修复、继续或缩减 |
| **M5-A：专注陪伴** | 单个专注会话的开始、暂停、结束及休息反馈；与日常提醒协调 | M4 价值成立 | 用户认为它改善专注体验，而非增加另一套打断 |
| **M5-B：轻量任务陪伴** | 为当前会话添加一个任务名称、完成／放弃和角色反馈 | 专注陪伴得到正面反馈 | 用户能解释其相对纯计时的额外价值；不扩展列表、项目或复杂排期 |
| **M5-C：公开分发** | 安装、升级、回滚、签名、反馈入口和维护策略 | M4 后明确决定公开，并具备维护能力 | 普通用户可独立安装与退出；素材分发范围明确；预算和维护责任确定 |

### 对原计划的调整

- 测试构建与分发能力前移到 M0，避免每轮实测都要求测试者配置开发环境。
- M2 与 M3 并行，角色美术不再阻塞提醒价值验证；并行工作不等于双角色日用版已完成。
- 必要设置随功能交付，不积压成一个过晚的“大设置阶段”。
- 性能和可靠性贯穿开发；公开分发是条件分支，不要求先把专注、任务功能全部做完。
- 6—12 个月是复盘窗口，不是必须完成全部功能的期限。范围超出人力时缩减后续功能，不降低双平台验收标准。
- 阶段编号不等于发布版本号。每次版本发布在对应 Goal 中明确范围与产物，不通过改版本号代替验收。

## 3. 产品规则、架构与角色资源

### 陪伴与提醒

陪伴感来自角色对用户操作的清晰回应，不靠额外随机通知维持存在感。短句简短、符合角色性格，不责备用户，也不将未完成提醒解释为失败。

2026-09-23 Windows 所有者试用反馈：现有通用提醒窗让角色像附属装饰，互动感不足。后续提醒到期应先由当前角色做一次动作并说符合性格的短句，旁边显示带角色形象、可直接“完成／稍后”的贴身对白。它仍是用户明确启用的三类提醒，不增加随机主动通知；手动查看待处理不重播到期动作。穿透和隐藏状态下保留独立可交互入口，Rust 仍唯一负责提醒进度。三月七采用活泼亲近的口吻，雷电将军按所有者选择采用克制正式的“将军”口吻；原作短句可作为候选，但须逐条核对情境与分发范围，所有者最终验收。

第一组实用功能固定为喝水、起身活动、休息眼睛三类内置提醒，各自支持开关和间隔调整。不是自由创建任意日程的提醒平台。

提醒保持以下共同规则：

- 每项完成后独立重新计时；自动收起不算完成。
- 未回应保留待处理状态，不因下一次轮询反复弹出。
- 全局稍后期间，新到期事项也保持安静；结束后合并提示。
- 提供固定的待处理查看入口，解决“不能反复提醒，但也不能找不到”的问题。
- 暂停与隐藏是不同操作；隐藏角色不隐式修改提醒进度。
- 活动时段外不主动提示，恢复时合并处理，不补弹所有错过的周期。
- 气泡不抢焦点；穿透模式必须仍有可确认提醒的入口。采用独立可交互气泡窗口，角色窗口继续保持用户选择的模式。
- 首次使用先确认提醒设置再启用；间隔与活动时段由用户设置，具体预置值在提醒 Goal 的交互规格中明确，不能被当作健康建议。
- 开机启动为后续可选设置，默认关闭。

### 技术职责

**前端负责角色表现，Rust 负责需要脱离页面持续运行的应用状态。**

| 子系统 | 单一职责与边界 |
|---|---|
| 动画与输入 | TypeScript 纯模型处理动画优先级、时序和明确动作事件；不拥有提醒进度 |
| 角色资源 | 定义图集、动作能力和情境短句；角色 ID 不得进入通用业务分支 |
| 提醒引擎 | Rust 管理到期、完成、稍后、暂停与恢复；UI 隐藏不影响状态权威 |
| 桌面控制 | Rust 管理托盘、窗口、穿透和位置；平台差异封装在适配层 |
| 持久化 | Rust 作为唯一写入者；配置带版本，迁移前备份，写入失败不伪装成功 |
| 界面 | 显示状态快照、发送明确命令，不自行复制业务计时或修改存储 |

以上是目标架构，其中提醒、托盘与持久化尚未实现。原文档中“未来由前端提醒服务管理计时”的设想已被替代，不再保留两套状态来源。

最小接口按能力扩展：

- 角色定义增加动作能力及情境短句映射。
- 桌面控制提供显示、隐藏、模式切换、重置位置与退出。
- 提醒提供读取快照、完成单项、全局稍后、暂停／恢复、修改设置和收起展示。
- 收起展示只影响呈现状态；角色切换只影响表现与选中角色。
- IPC 使用有类型的输入、状态快照和错误结果；不提前建设通用插件协议或公共 SDK。

动画使用单调时间；提醒使用可持久化的截止时间并处理睡眠与时钟变化。睡眠恢复只评估当前状态，不重播历史事件。专注计时接入后与日常提醒共用展示协调规则，避免两套功能同时弹出。

### 角色资源长期管理

保持少量、经过验收的内置角色，不建立商店或任意外部脚本导入能力。

制作流程固定为：**所有者确认候选与参考 → 样例验收 → 动作制作 → 图集与方向检查 → 实际尺寸播放检查 → 双平台接入验收。**

每个角色保留来源、版本、使用范围、动作能力、已知限制和验收记录。应用仅要求实际使用的动作，不为兼容旧 Codex 的所有状态而强迫新增角色制作无用动画。旧封存包继续保持不变。

第二角色姓名尚未确定：它是角色制作 Goal 的必需输入，由所有者确认，执行者不得自行选定。

## 4. 质量、反馈与调整方向

### 验证体系

- **每次代码变更**：相关单元测试、类型检查、构建、依赖边界检查及双平台 Rust 检查。
- **每个里程碑**：两平台使用同一提交和验收清单，集中测试新增体验并回归原有能力。
- **发布候选**：安装、升级、卸载、数据迁移、回滚、睡眠恢复与长期运行检查。
- **性能**：M0 建立两台实际设备上的 CPU、内存和响应基准；常驻阶段验证空闲与长时间运行，避免把单一平台数字照搬到另一平台。
- **证据**：构建成功、自动测试、人工实测和用户价值反馈分别记录，不相互替代。

重点测试场景包括：多项同时到期、稍后期间继续到期、无回应后重新查看、切换角色、隐藏与穿透、睡眠与重启、损坏配置、写入失败、显示器变化，以及动画循环或监听重复启动。

### 两周试用与判断标准

默认招募所有者和少数朋友，目标约 3—5 人，覆盖两平台；这是发现问题的小样本，不用于宣称普遍效果。

采用简短手工反馈，关注：

- 哪一次提醒确实有帮助？
- 哪一次打断令人厌烦，用户如何处理？
- 为什么继续打开、暂停或关闭桌宠？
- 有没有卡顿、窗口丢失、无法退出、状态丢失或安装困难？

**继续投入条件**：至少所有者和另一位参与者能给出持续帮助的具体例子，愿意继续使用，且没有未解决的严重稳定性问题。点击完成次数只代表操作记录，不代表真实健康行为。

**调整或暂停规则：**

- 出现数据丢失、无法退出或明显妨碍工作的问题，先停止扩大试用。
- 提醒有价值但烦，优先改节奏和展示，不增加提醒种类。
- 陪伴受欢迎、提醒无价值，保留陪伴体验，暂停提醒功能扩张并共同复盘。
- 连续两轮针对性调整后仍没有明确价值，暂停该方向，不按原路线惯性开发。
- Mac 测试或角色素材延期时，可推进独立模块，相关里程碑保持未完成。

### 隐私、分发与成本

数据默认留在本机，不建设账号、云同步或自动遥测后台。反馈和诊断由用户主动提供；不默认采集其他应用内容、窗口标题、截图或任务文本。

早期提供可追溯的测试产物与手工升级方式，先建立备份、迁移和回退能力。公开分发前，再处理签名、素材分发范围、安装支持和维护预算；自动更新只有在手工升级及回滚可靠后才进入范围。

主要持续风险是双平台测试人力、美术反复生成、通知疲劳、时间恢复逻辑和分发维护成本。所有这些都通过阶段验收控制，不以增加抽象层或提前建设平台来解决。
