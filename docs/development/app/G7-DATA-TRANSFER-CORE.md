# G7-B2 后台数据集切换协议

本阶段只提供本地后台核心。导入文件选择、预览、确认和导出界面尚未接入；不能把它称作可用的数据迁移功能。

## 数据布局与启动顺序

应用先在原配置目录持有 `instance.lock`，再解析数据集协议，最后才启动位置、角色和提醒的写入者。没有 `data-set-activated.json`、`active-data-set.json` 和 `pending-import.json` 时，三个 Store 继续使用原平铺文件，不自动迁移旧数据。首次准备的集合放在 `data-sets/<应用生成的 32 位随机十六进制 ID>/`，固定含三个文件。无历史保存位置写成 `{"version":1,"placement":null}`，不伪造坐标。原平铺文件和旧数据集不会自动删除。

`active-data-set.json` v1 只含 `version`、`setId`、`transactionId`。`pending-import.json` v1 还含准备时的 `baseSetId`、`baseTransactionId` 和三个固定文件按名称、长度、内容顺序计算的 SHA-256 摘要。永久的 `data-set-activated.json` v1 只含 `version:1` 和 `activated:true`，不存路径或集合 ID。标识只允许应用生成的 32 位小写十六进制字符；记录不接受额外字段或任意路径。摘要用于发现准备后的意外变化，不是签名或恶意篡改防护。

准备操作在当前运行中不改变任何 Store 路径：先由各模块验证当前 v1 格式、角色 ID、提醒状态和未知字段，再写完整新集合并读回复核，最后原子替换待导入记录。单次集合内容上限为 1 MiB。已有待导入记录时拒绝再次准备。后续 UI 必须明确说明“下次启动生效”。

下次启动若活动指针仍等于准备时基线，校验完整集合及摘要后，先原子写入并读回永久切换标记，再原子切换活动指针；三个 Store 从同一个解析结果读取。若在标记写好、指针未写好时退出，保留的完整待办可在下一次启动继续；标记写入失败则不切换。若指针已是该事务的新集合，只清理旧待办，不重新写文件，也不拿旧摘要对比之后的正常保存。待办删除失败可留到再下次启动。标记存在而指针丢失、标记丢失而指针存在、基线不匹配、未知/损坏记录或集合损坏时，三个 Store 本次均不获得持久写入路径，原件与诊断码保留；不回退混用平铺文件。只有首次切换标记已写好、指针未写好且完整待办仍匹配原平铺基线时可以继续提交。指针替换失败保留待办、标记和旧文件，本次只读，后续启动可重试。

本协议只能协调使用当前锁协议的进程。旧版程序不认识新指针和锁；回退旧版之前必须先退出当前版本，旧版看到的是保留的原平铺文件，不能视为新版本数据的完整回退。记录元数据已确认存在后，即使随后的读取报告“不存在”，也按读取故障保护，不能解释为第一次运行。单文件写入和指针替换执行写入同步，但测试只证明进程退出与注入的 I/O 失败恢复，不证明突然断电下的目录元数据持久性。Windows 和 macOS 的桌面实机验收仍未完成。
