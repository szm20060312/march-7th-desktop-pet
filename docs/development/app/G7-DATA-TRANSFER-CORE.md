# G7-B2 后台数据集切换协议

本阶段只提供本地后台核心。导入文件选择、预览、确认和导出界面尚未接入；不能把它称作可用的数据迁移功能。

## 数据布局与启动顺序

应用先在原配置目录持有 `instance.lock`，再解析数据集协议，最后才启动位置、角色和提醒的写入者。没有 `active-data-set.json` 和 `pending-import.json` 时，三个 Store 继续使用原平铺文件，不自动迁移旧数据。首次准备的集合放在 `data-sets/<应用生成的 32 位随机十六进制 ID>/`，固定含三个文件。无历史保存位置写成 `{"version":1,"placement":null}`，不伪造坐标。原平铺文件和旧数据集不会自动删除。

`active-data-set.json` v1 只含 `version`、`setId`、`transactionId`。`pending-import.json` v1 还含准备时的 `baseSetId`、`baseTransactionId` 和三个固定文件按名称、长度、内容顺序计算的 SHA-256 摘要。标识只允许应用生成的 32 位小写十六进制字符；记录不接受额外字段或任意路径。摘要用于发现准备后的意外变化，不是签名或恶意篡改防护。

准备操作在当前运行中不改变任何 Store 路径：先由各模块验证当前 v1 格式、角色 ID、提醒状态和未知字段，再写完整新集合并读回复核，最后原子替换待导入记录。单次集合内容上限为 1 MiB。已有待导入记录时拒绝再次准备。后续 UI 必须明确说明“下次启动生效”。

下次启动若活动指针仍等于准备时基线，校验完整集合及摘要后，只原子切换活动指针；三个 Store 从同一个解析结果读取。若指针已是该事务的新集合，只清理旧待办，不重新写文件，也不拿旧摘要对比之后的正常保存。待办删除失败可留到再下次启动。基线不匹配、未知/损坏指针、待办或集合损坏时，三个 Store 本次均不获得持久写入路径，原件与诊断码保留；不回退混用平铺文件。指针替换失败同样保留待办和旧文件，本次只读，后续启动可重试。

本协议只能协调使用当前锁协议的进程。旧版程序不认识新指针和锁；回退旧版之前必须先退出当前版本，旧版看到的是保留的原平铺文件，不能视为新版本数据的完整回退。单文件写入和指针替换执行写入同步，但测试只证明进程退出与注入的 I/O 失败恢复，不证明突然断电下的目录元数据持久性。Windows 和 macOS 的桌面实机验收仍未完成。
